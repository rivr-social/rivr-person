# Autobot & agents

## What it is

Autobot is the assistant that lives on your instance — and, more importantly,
the control plane that decides **what it may do on your behalf.**

Four things sit under that heading:

- **The assistant itself** — a chat you can talk to, which knows your profile,
  your documents, and whatever knowledge graphs you've folded in.
- **Personas** — additional named identities you own. A persona has its own
  face, voice, personality sliders, and its own private knowledge graph.
- **Connectors** — links to outside services (Google, Slack, Notion, Telegram…)
  so the assistant can read and act there.
- **MCP** — the protocol endpoint that lets an external AI agent act as you,
  with every call written to a provenance log.

The talking, animated version of the assistant has its own page:
**[Live avatar & voice](/docs/wiki/live-avatar)**.

## How to chat with your assistant

1. Go to `/autobot/chat`, or use the floating assistant bubble that rides on
   your profile.
2. Type. The assistant answers with your own context available to it.
3. Open the settings drawer to change the model, the voice mode, and which
   persona knowledge graphs are folded into the main assistant's context.

![The autobot chat workspace with the settings drawer open: the model select, profile selector, and the agent-context inspector with the soul-prompt override](/wiki/autobot-agents/person-22-autobot-drawer.png)

Model providers are configured by the instance, not per-conversation: OpenAI,
Google, a connected Claude Code credential, or a local Ollama server.

## How to create a persona

A persona is a second identity you own — a character the assistant can speak as,
with its own knowledge.

1. Go to `/personas/new`.
2. Fill in the character sheet:
   - **Name** (required), **Tagline**, **Username**, **Pronouns**, **Bio**
   - **Voice / speaking style** — *terse*, *warm*, *formal*, *technical*, or
     *playful*
   - **Language** and an **avatar image URL**
   - **Operating mode** — see the gating table below
   - **Skill sliders** (0–100): federation savvy, technical depth, organizing,
     public voice, risk tolerance, creative output, conversational warmth, speed
3. Save. Manage personas from `/profile?tab=personas` — `/personas` simply
   redirects there.
4. Edit later at `/personas/[id]/edit`.

![The persona creator's character sheet: Identity fields with the Stats, Skills, Inventory, and Appearance sections of the RPG-style builder](/wiki/autobot-agents/person-23-personas-new.png)

<Callout type="note" title="Switching into a persona changes the app">
  When a persona is the active actor, `/settings` stops showing the normal
  settings tabs entirely and becomes that persona's editor instead — the same
  character sheet as `/personas/[id]/edit`. There is no persona-flavoured
  variant of the settings form to see: the page returns the persona editor
  before it ever reaches the settings tabs.
</Callout>

### Persona knowledge graphs

Each persona has its own scoped knowledge graph, reachable at
`/api/personas/[id]/kg/{docs,graph,stats,chat}`. You can list and create docs in
that scope, query the subgraph, read counts, or chat against it directly. All of
them refuse politely if the persona isn't yours — a persona you don't own is
reported as *not found*, so existence isn't leaked.

## How the assistant is allowed to act

Every action the assistant can take is classified by risk, and each persona runs
in one of three **operating modes**:

| Mode | Behaviour |
| --- | --- |
| `direct-only` | **Most restrictive.** Every action needs approval, whatever its risk — the persona only acts when you explicitly say so |
| `approval-required` | Low-risk actions run straight through; medium and high risk queue an approval |
| `delegated` | **Broadest autonomy.** Low and medium risk run straight through; only high-risk actions still queue an approval |

Risk is mapped per action — reading the knowledge graph is *low*, creating a
post is *medium*, and anything financial, destructive, or membership-changing is
*high*.

<Callout type="note" title="direct-only is the strictest setting, not the loosest">
  The name reads like "acts directly", but it means the opposite: *direct*
  instruction is required for everything. If you want a persona that mostly
  runs on its own but pauses on money and deletions, you want
  `approval-required`, not `direct-only`. A per-persona override list can
  auto-allow specific action types ahead of the mode check.
</Callout>

<Callout type="warning" title="The approvals queue has no screen yet">
  Approvals are created, stored, and resolvable through
  `/api/autobot/approvals` and `/api/autobot/approvals/[id]/resolve`, and the
  decision history is queryable at `/api/autobot/audit-log`. **There is no
  approvals UI in this app** — nothing renders that queue today. Don't confuse
  it with *device approvals* (Settings → Assistant → Access), which is a
  different feature for MCP login codes.
</Callout>

## How to connect an outside service

1. Go to `/settings` → the **Assistant** tab → **Connectors**.
2. Pick a service and press connect. You're sent to that provider's consent
   screen and returned here.

The user-connectable set is thirteen providers: **Google Drive, Google Calendar,
Gmail, Notion, Telegram, WhatsApp Business, Signal, Slack, Facebook, Instagram,
Substack, Luma, and X**. The first is labelled *Google Drive* in the UI and
covers Drive files as well as Google Docs — its internal provider id is
`google_docs`, which is the name you'll see in API payloads. A second group —
**Cloudflare, Squarespace, Namecheap** — exists for DNS writes and is used by
the [Builder](/docs/wiki/builder).

![The assistant Connectors panel: the agent-connectors explainer, and a provider card (Google Drive, disconnected) with capability chips, the Share-with-personas toggle, and Set Up Provider](/wiki/autobot-agents/person-24-connectors.png)

Beyond OAuth, each connector supports three operations:

- **Setup** — supply credentials or configuration by hand (this is how Telegram
  bot tokens are validated).
- **Test** — check the stored credential against the live provider.
- **Sync** — pull data in. Not every connector implements it; those return a
  clear *"Sync is not implemented for this connector yet."*

<Callout type="warning" title="Not every connector encrypts its config at rest">
  OAuth tokens live in the accounts table. Connector *config* values are stored
  in the agent's metadata, and only four providers — **Claude Code, Cloudflare,
  Squarespace, Namecheap** — currently run their secrets through the encryption
  envelope. Secrets are always redacted on the way back out to the browser
  (you'll see `__stored__`, never the value). Instance operators should set
  `CONNECTOR_ENCRYPTION_KEY` explicitly in production; otherwise the key is
  derived from `AUTH_SECRET`, and rotating that would make stored secrets
  undecryptable.
</Callout>

## How to let an external agent act as you (MCP)

1. Go to `/settings` → **Assistant** → **Access** and mint an MCP token.
2. Point your agent at `POST /api/mcp` with that token as a bearer credential.
   Discovery is advertised at `/.well-known/mcp`.
3. For a device that can't hold a browser session, use the device flow: the
   device shows a code, you approve it at `/mcp/authorize?user_code=XXXX-XXXX`,
   and it's issued a token. Pending codes also appear under **Access → Device
   Approvals**.

![The MCP device-authorization page: "Authorize MCP Access", the signed-in identity, the request code, the 30-day grant explanation, and the Approve and Deny buttons](/wiki/autobot-agents/person-25-mcp-authorize.png)

**Twenty-eight tools** are registered. All of them are namespaced `rivr.<area>.`:

| Area | Tools |
| --- | --- |
| Instance & places | `rivr.instance.get_context` · `rivr.places.list` |
| Profile & personas | `rivr.profile.get_my_profile` · `rivr.profile.update_basic` · `rivr.personas.list` |
| Posts & resources | `rivr.posts.create` · `rivr.posts.create_live_invite` · **`rivr.posts.delete`** · `rivr.resources.update` |
| Events & groups | `rivr.events.create` · `rivr.events.rsvp` · `rivr.events.append_transcript` · `rivr.groups.join` |
| Offerings & money | `rivr.offerings.create` · **`rivr.thanks.send`** |
| Knowledge graph | `rivr.kg.list_docs` · `rivr.kg.push_doc` · `rivr.kg.query` · `rivr.kg.chat` |
| Audit | `rivr.audit.recent` |
| Deploy | `rivr.deploy.get_capability` · **`rivr.deploy.self_deploy`** · **`rivr.deploy.restart_autobot`** · **`rivr.deploy.docker_rebuild`** |
| Sandbox | `rivr.sandbox.status` · `rivr.sandbox.check_operation` |
| Dispatch & connectors | `rivr.dispatch.send_message` · `rivr.connectors.sync` |

<Callout type="warning" title="Some of these are powerful — read the bold ones twice">
  An MCP token is not a read-only key. `rivr.posts.delete` removes content,
  `rivr.thanks.send` moves value to another agent, and the four `rivr.deploy.*`
  tools can pull-and-rebuild this instance, restart the autobot sidecar, or
  trigger a Docker rebuild. The deploy tools are gated by the instance's deploy
  capability and refuse on shared instances, but on your own sovereign box they
  are live. Scope tokens deliberately, and review `rivr.audit.recent` after
  handing one out.
</Callout>

**Every tool call is logged** to the provenance log with a full audit trail —
that is the point of the design, and no tool is allowed to bypass it.

## Good to know

- **Personas resolve ownership against their controller**, not against
  themselves — a tool acting as your persona is authorised as you.
- **Account deletion is interactive-UI-only** with typed confirmation — there
  is no MCP tool for it. That is not a general rule about destructive actions,
  though: post deletion, thanks transfers, and instance rebuilds all have tools
  (see the table above).
- **`/api/autobot`, `/api/personas` and `/api/agent-hq` are owner-only** at the
  edge. A federated visitor browsing your instance is refused before the
  handler runs. The one deliberate exception is
  `/api/autobot/gpu/worker-source`, which is on the public-route allowlist so
  that a booting GPU box can fetch the plain worker source anonymously; the
  public-route check runs before the owner gate, so that prefix is genuinely
  open. It serves source code only — no secrets, no state.
- **Digital-twin uploads still work; the video pipeline does not.** You can
  upload host video, reference portraits, idle video, and background plates
  (up to 32 assets). The generative video-render pipeline that used to consume
  them was removed on 2026-07-22 — it drove a worker that never existed in this
  repo, and the [live-avatar lane](/docs/wiki/live-avatar) supersedes it.

### About "Agent HQ"

You'll see the name in URLs (`/settings?tab=agent-hq`) and across
`/api/agent-hq/**`. It is **not a page** — there is no `/agent-hq` route here.
What survives of it is split in two:

- Its per-agent tabs were re-homed into **Settings → Assistant** (Identity,
  Roles, Knowledge, Voice, Access, Connectors).
- Its filesystem/vault half surfaces as the **Docs tab** on your profile — see
  [Docs & vault](/docs/wiki/docs-vault).

The remaining routes — tmux-backed agent terminal sessions, teams, launchers,
session templates — are **API-only host-operator surface** with no page in this
app, and they refuse entirely unless the instance is sovereign
(*"Agent terminal control is only available on sovereign instances."*).
